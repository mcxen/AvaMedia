# 视频瘦身

入口位于「视频 → 视频瘦身」，文件导入路由也提供这个工具。支持批量、任务编辑、停止分析和队列取消。输出另存，保留源文件。

工具针对高码率重新导出、画面内容简单但文件体积大的视频，目标是减少当前画面的编码体积。它不能还原已经丢失的细节，也不能反推出历史原文件的大小。

## 使用

1. 添加视频，选择保真 / 均衡 / 更小、HEVC / H.264、MKV / MP4。
2. 可点击「分析体积」查看预计体积和采样质量；未预分析时，队列会自动分析。
3. 加入队列。保持分辨率、帧率，直拷全部音轨和字幕轨。MKV 还复制附件与字体。

预计节省不足 5% 时不建议加入队列；实际节省不足 5% 时清除临时输出并说明原因。编码失败、源文件变化或取消时也清除临时文件，原文件保留。

## 实现

`VideoSlimming` 是界面分析与队列执行的共享服务。最多六段均匀分布的样本，加一段从八个短时间窗中找到的较大运动样本，每段最多三秒。源画面样本以 FFV1 保存，不经过有损编码。全部音轨独立按码率元数据估算，缺失时在三个时间窗采样音频包，避免流复制的音频预滚动偏移参考画面时间戳。

采样通过 FFmpeg 的 `-progress` 帧数确认画面已经写入，再读取样本信息。TS 等文件在片尾定位可能得到零帧并成功退出；这种只有容器头的 MKV 不进入探测和画质比较。空样本删除后，最多向前移动一段时长和至少 12 秒分别重取，使用 `-noaccurate_seek` 从附近关键帧开始解码并归零时间戳；实际有效样本时长用于体积推算。重试仍无帧时报告采样位置与时长／时间戳异常，编码器或写入错误直接报错。[FFmpeg 参数说明](https://ffmpeg.org/ffmpeg.html)

在 CRF 16–42 中搜索。试编码和整段导出均使用同一个 x264 / x265 软件编码器、medium 档位、像素格式和线程数，不将软件测出的参数直接套在 GPU 上。优先选用满足质量约束且预计体积最小的候选。

| 档位 | 平均 SSIM 至少 | 每段 SSIM 至少 | XPSNR 最低分量至少 |
|---|---:|---:|---:|
| 保真 | 0.995 | 0.992 | 40 dB |
| 均衡 | 0.990 | 0.987 | 38 dB |
| 更小 | 0.980 | 0.977 | 35 dB |

使用 FFmpeg 内置 SSIM；有 XPSNR 时同时约束每段样本的最低色彩分量评分。当前内置 FFmpeg 含这两个滤镜，不新增模型下载。缺少 XPSNR 的外部引擎使用 SSIM，并在日志中标明 XPSNR 不可用。

编码时使用 `enc_time_base=demux` 保留时间精度，比较前将时间戳起点归零，使用 `ts_sync_mode=nearest` 避免 Matroska 毫秒舍入造成相邻帧错配，关闭末帧重复。质量分来自采样，不能保证整段每帧都达到相同评分，也不代表无损。预计体积由样本实际视频及全部音轨体积推算；字幕、附件和未采样场景会影响误差。

预分析结果只在源路径、体积、修改时间、档位、编码、格式与线程数相符时复用。输出先写相邻临时文件，检查时长、尺寸、音轨与字幕轨数量和实际节省，再原子移动到目标位置。

## 当前范围

支持单视频轨、逐行 SDR 视频。内嵌封面和缩略图不计入视频轨数量，也不参与采样或视频编码；导入信息、色彩检查和处理参数均使用真实视频轨。采样、复杂度分析、画质比较和导出使用 FFmpeg 的 `V` 流选择器排除封面与缩略图，与它们在文件中的排列顺序无关。[FFmpeg 流选择器说明](https://ffmpeg.org/ffmpeg.html#Stream-specifiers)

HDR / Dolby Vision、隔行或多视频轨文件会给出明确提示。MP4 无法直拷的音轨、字幕或附件要求改用 MKV；MKV 无法原样承载的 `mov_text` 字幕要求改用 MP4。

## 用户指定的端到端实践

验证程序 `tests/AvaMedia.VideoSlimmingTests` 仅在显式运行时执行，不加入常规验证脚本。

```sh
.tools/dotnet/dotnet run --project tests/AvaMedia.VideoSlimmingTests -c Release -- \
  /absolute/path/to/ffmpeg /absolute/path/to/ffprobe artifacts/video-slim-practice
```

要求使用空输出目录。程序生成 60 秒的 320 × 180 动态测试画面，将其放大至 1280 × 720 并模糊，以约 600 kbps 视频及 64 kbps 音频得到约 5 MB 源文件。随后按 16 Mbps H.264 CBR 重新编码，并显式使用 filler 数据将体积放大至约 120 MB。这是人为制造冗余的样本，不代表所有大视频。

瘦身通过 `CreateJobs → JSON 参数往返 → QueueService → MediaEngine.Execute → VideoSlimming` 的真实生产路径完成。程序测量整段 SSIM / XPSNR、时长、分辨率、帧率、全部解码帧数、音频码流哈希与源文件哈希，将媒体文件及 `report.json` 保留在指定目录。

修复代码后需要继续同一个场景时，可将原样本目录作为第四个参数，复用同一组源文件，结果仍写入新的空目录。

### 2026-10-08 本地结果

实际通过生产队列完成，全部断言通过：

| 阶段 | 实际体积 |
|---|---:|
| 低清源视频 | 5,029,204 B（5.03 MB） |
| 高 CBR 膨胀视频 | 120,129,430 B（120.13 MB） |
| 瘦身输出 | 4,137,004 B（4.14 MB） |

选择 HEVC medium CRF 25，七段共 21 秒采样。预计输出 4,173,158 B，实际节省 96.5562%。整段输出相对膨胀输入 SSIM 为 0.996596、XPSNR 为 38.4047 dB；相对最初低清源 SSIM 为 0.996607、XPSNR 为 38.4055 dB。

1280 × 720、24 fps、60 秒、1440 个解码帧均保留，音频码流哈希一致，两个源文件的 SHA256 未变化。媒体及完整报告保存在 `artifacts/video-slim-e2e-20261008-aligned/`。本次是媒体处理与生产队列的端到端实践；桌面窗口完成编译检查，未执行桌面点击验收。
