# Huihui Qwen3.5 9B 本机试跑（2026-10-14）

## 配置与范围

- Apple M4、16 GiB 统一内存；其他日常应用仍在运行。
- Huihui Qwen3.5 9B abliterated，Q4_K_M 主权重加 f16 视觉投影，合计 6,545,211,264 字节。通过生产 `ModelStore.DownloadAsync` 下载并校验 SHA256，固定来源与校验值见 `Assets/SummaryModels.json`。
- llama.cpp b11476，16K 上下文，单 slot，关闭 thinking；实际后端回报 `Metal / CPU`。
- 9B 为本地增强档默认值，4B 为可选基础档。标签识别、服装分割、DINOv2 特征与语义辅助模型保留原职责；9B 增加画面描述、文本总结与 VL 命名能力。

## 单次观察

| 项目 | 实测 | 判断 |
| --- | --- | --- |
| 首次模型准备 | 18.0 秒，含文件校验与服务启动 | 正常启动 |
| 服饰单图 | 34.6 秒 | 白色无袖上衣、细框眼镜、灰白格纹背景可对应画面；衣领裁剪、左右手和指甲归属有过度推断 |
| 30 秒视频、4 帧，现有画面总结流程 | 214.4 秒，包含逐帧观察、分段复核与总结 | 流程正常结束，但把烹饪概括成“人物近距离互动”，遗漏切肉等主要动作；语义不通过 |
| 同 4 帧直接多图描述 | 56.1 秒，不含该轮 10.5 秒模型准备 | 能描述烹饪、切肉、碎花短袖和围裙；仍把脂肪写成带皮，并补写采样间“拨入锅”的动作 |

前一条视频调用通过生产 `MediaCaptionService` 与 `MediaCaptionEvidence`，后一条为 `LocalSummaryModel` 的一次多图调用，用于区分模型可表达的信息与业务流程输出。两者提示、请求数、上下文和处理阶段不同，不能作为严格性能对比。结果提示现有结构化流程也可能损失有效信息，尚未做因果验证或改写该流程。

单图、视频调用均正常完成，证明这台 M4 16GB 能运行该模型。样本量很小，不代表稳定吞吐、长期批处理、准确率或拒答率；此次没有运行完整标签/服装聚类队列、桌面界面验收或安装包验收。不能仅用这次结果声称 9B 比 4B 更准确。

## 内存与证据边界

第一轮整机 swap 由约 5.49 GiB 增至约 7.83 GiB，其他应用同时运行，不能把全部变化归因于模型。补采的 llama-server RSS 峰值约 2.30 GiB、某时刻 vmmap 的 physical footprint 峰值约 2.0 GiB，都不能代表包含映射权重、GPU 和其他进程的整机内存需求。原采样器仅追踪直接子进程，遗漏 llama-server 孙进程，其 `peak_model_rss_kib=0` 无效，已另行补采。

临时诊断程序最初存在 System.Text.Json 引用版本冲突，误启动的旧程序已中止，不计入有效试跑；修正为桌面程序相同依赖后，直接多图诊断编译与执行成功。

本地证据目录：`artifacts/huihui9b-trial-20261014/`，包含采样图、`result.json`、`direct-video-result.json`、运行日志、资源记录和证据哈希清单。该目录不纳入发布包。Luna agent 已独立只读复核清理范围、接入路径与结论边界。
